# iroh-go

Go bindings for [iroh](https://iroh.computer) — peer-to-peer QUIC connections
dialled by public key — **without CGO**.

```go
ep, _ := iroh.Bind(ctx, iroh.Options{ALPNs: [][]byte{[]byte("my/1")}})
defer ep.Close(ctx)

conn, _ := ep.ConnectTicket(ctx, ticket, []byte("my/1"))
send, recv, _ := conn.OpenBi(ctx)

io.Copy(send, os.Stdin)
send.Close()
io.Copy(os.Stdout, recv)
```

```
go get github.com/discobox-ai/iroh-go
```

## Why no CGO

The existing [iroh-go](https://git.coopcloud.tech/decentral1se/iroh-go) is
generated by `uniffi-bindgen-go`: it needs `CGO_ENABLED=1`, a C toolchain, and
ships Linux musl only. This one takes the other trade-off, the same one
[turso-go](https://github.com/tursodatabase/turso) makes — a prebuilt Rust
`cdylib` loaded at runtime through
[purego](https://github.com/ebitengine/purego). So this works:

```
CGO_ENABLED=0 GOOS=windows GOARCH=arm64 go build ./...
```

No C compiler, no cross toolchain, no build tags to remember, and `go test`
runs the same way your users build.

## Platforms

| OS      | amd64 | arm64 |
| ------- | ----- | ----- |
| Linux   | ✅    | ✅    |
| Linux (musl, `-tags musl`) | ✅ | ✅ |
| macOS   | ✅    | ✅    |
| Windows | ✅    | ✅    |

Each platform's library lives in its own Go module under `libs/`, so `go build`
downloads only the one you need rather than all of them. Those modules are
versioned on iroh's major and minor -- `libs/*/v1.0.x` is iroh 1.0 -- with the
patch reserved for changes to the binding's own Rust shim. `iroh.IrohVersion()`
reports the exact upstream version compiled into the library you loaded. Linux builds pin a
glibc floor of 2.17, so they run on distributions much older than the machine
that built them.

Android and iOS are reachable in principle but need `CGO_ENABLED=1` for purego
itself, so they are not wired up.

## API

Concepts and names follow iroh; the shapes follow Go.

| iroh                        | here                                            |
| --------------------------- | ----------------------------------------------- |
| `Endpoint::bind`            | `iroh.Bind(ctx, Options{})`                     |
| `endpoint.connect`          | `ep.Connect(ctx, addr, alpn)`                   |
| `endpoint.accept`           | `ep.Accept(ctx)` — returns a handshaken `*Conn` |
| `connection.open_bi`        | `conn.OpenBi(ctx)`                              |
| `send_stream.write_all`     | `send.Write(p)` — `io.Writer`                   |
| `recv_stream.read_to_end`   | `io.ReadAll(recv)` — `io.Reader`, `io.EOF`      |
| `send_stream.finish`        | `send.Close()`                                  |
| `EndpointTicket`            | `iroh.Ticket`                                   |

Every call that waits takes a `context.Context`, and cancelling one really does
cancel the operation inside iroh rather than abandoning it. Streams also
support `SetReadDeadline`/`SetWriteDeadline` like `net.Conn`, for the
`io.Reader`/`io.Writer` methods that take no context.

Errors carry a `Kind` and match sentinels through `errors.Is`:

```go
if errors.Is(err, iroh.ErrClosed) { ... }
```

### net.Conn and net.Listener

A QUIC stream is an ordered reliable byte stream between two authenticated
parties, which is what `net.Conn` describes. So `net/http`, gRPC, `crypto/ssh`
and anything else written against the standard interfaces runs over iroh
unchanged:

```go
listener := ep.Listener(iroh.ListenOptions{
    Authorize: func(c *iroh.Conn) error { ... },  // optional, refuses with a reason
})
http.Serve(listener, handler)
```

```go
client := &http.Client{Transport: &http.Transport{
    DialContext: func(ctx context.Context, _, _ string) (net.Conn, error) {
        return conn.OpenConn(ctx)   // one stream per request
    },
}}
```

`RemoteAddr()` is the peer's endpoint id, already proven by the handshake, so a
server builds a principal from the connection rather than asking the client who
it is. `CloseWrite()` half-closes, which is what hijacked HTTP connections and
`crypto/ssh` need.

### Not yet covered

The first cut is core networking. Missing, in rough priority order: the
`Incoming`/`Connecting` split and 0-RTT (`Accept` hands back an already
handshaken connection); watchers for address, home-relay and path changes;
`ServicesClient` (ping, metrics, diagnostics); and protocol handlers driven
from Rust. Nothing in the design blocks them.

## How it works

```
your Go code
      │
   iroh (this package)              context.Context, io.Reader/Writer, error
      │
   internal/ffi                     purego trampolines + one completion pump
      │  ▲
      │  └── one OS thread parked in iroh_completion_wait, for the whole process
      ▼
   libiroh_go.so                    flat C ABI: scalars and pointers only
      │
   iroh 1.0.3 (Rust)                tokio, quinn
```

Three constraints shaped this:

- **purego allows ~2000 callbacks per process, ever.** So Rust never calls back
  into Go. Async operations return an id immediately and post to one completion
  queue that a single Go thread drains, fanning results out over channels.
- **A blocking C call blocks its OS thread**, invisibly to the Go scheduler. One
  parked thread total, no matter how many streams are in flight.
- **Structs by value and floats are unsupported on some architectures.** Nothing
  crosses the boundary but scalars and pointers, so tier-2 targets stay open.

Rust also never retains a Go pointer past the call it was passed to: writes are
copied before the operation is spawned, and reads are copied out of buffers the
library owns.

## Development

Building the native library needs a Rust toolchain; using the package does not.

```
make lib        # build the cdylib for this machine into libs/<platform>/
make test       # go test with CGO_ENABLED=0
make race       # go test -race
make rust-test  # cargo test
make vet        # go vet, gofmt, cargo fmt, clippy
make cross      # check every platform still compiles without cgo
```

`make libs` cross-builds the shipping artifacts for release prep. The four
Linux targets — gnu and musl, both architectures — build from any host given
[cargo-zigbuild](https://github.com/rust-cross/cargo-zigbuild), which also pins
a glibc floor of 2.17 so they run on far older distributions than the build
machine.

macOS and Windows are built on a host of that OS, and the script says so and
skips them rather than failing. macOS cannot be cross-compiled at all: iroh
links the `SystemConfiguration` and `CoreFoundation` frameworks, which ship
only in Apple's SDK, licensed by Apple for use on Apple hardware. Windows can
be in principle, via cargo-xwin, but `ring` does not build that way — cargo-xwin
passes clang-cl style `/imsvc` include flags while `cc-rs` invokes plain
`clang`, which rejects them.

Cross-compiling only proves a library links, though. Since these are `dlopen`'d
at runtime with no fallback, a broken one fails in the user's process rather
than at their compile time — so the `build-libs` workflow runs the real Go
suite on real hardware for all eight before committing anything.

Try it end to end with two terminals:

```
go run ./examples/echo -offline listen
go run ./examples/echo -offline dial <ticket> "hello"
```

Drop `-offline` to go through n0's relays and reach a peer on another network.

### Escape hatches

- `IROH_GO_LIBRARY=/path/to/libiroh_go.so` loads a specific library.
- `IROH_GO_CACHE_DIR` changes where the embedded library is extracted.
- `IROH_GO_VERIFY_LIB=1` re-checks the extracted library's hash on every start.
- `-tags iroh_nolibs` omits the embedded library entirely; supply your own.
